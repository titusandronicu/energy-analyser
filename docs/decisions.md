# Decisions

The main product and technical decisions, newest first, each with the reason. Detailed plans for each change are in `context/changes/` (active) and `context/archive/` (done); the product requirements are in `context/foundation/prd-v3.md` and the ordered work in `context/foundation/roadmap.md`.

## 2026-10-05 (quality gates)

- **The suites from the test rollout now gate merges: `ci`, `smoke` and `integration` are required on `main` by a ruleset that also binds the owner (`context/archive/2026-10-05-testing-quality-gates-wiring/`; owner's decisions).** Before this, `main` had no protection and the checks were advisory.
  - **Ruleset `main-quality-gates`** (`.github/rulesets/main-quality-gates.json`): required checks `ci`, `smoke`, `integration`, no bypass actors, branches need not be up to date, no force push or deletion, so changes go through pull requests. Apply and recovery steps (disable enforcement if CI itself breaks) are in `docs/prerequisites.md`.
  - **The integration suite is its own CI job** with its own check name, so a red check names the suite and it still runs when smoke fails. The Supabase start is one shared composite action (`.github/actions/local-supabase`).
  - **Each gate was proven red by a deliberate break per risk** (#1 to #7, six throwaway PRs, none merged): `breaks.md` lists the check and test that caught each. The notes server limit is guarded by `ci` only; the integration suite guards the database limit.
  - **The post-edit check is the existing hooks** (`.claude/hooks/`, PR #106): proven by a break in `bill-forecast.ts`, recommended and not required.
  - **The ruleset requires check names, not workflow contents.** A pull request that edits `ci.yml` runs its own version of the workflow; accepted for a single owner.
  - **Not done: `deploy-production.yml` does not check that the SHA passed CI.** The manual deploy already needs the owner's approval on the `production` environment; a CI-green check on the SHA is a follow-up.

## 2026-10-05

- **The access and input tests (risks #6 and #7) add no production code; two differences between layers and one wide grant are pinned by named known-gap tests and not fixed (`context/archive/2026-10-02-testing-access-and-input-abuse/`; owner's decisions, test plan rollout Phase 3).** _Why:_ the guards already exist and RLS looked right on reading; what was missing was proof, and each fix (a database check, a column grant, a changed trim rule) is a product or security decision on production data.
  - **A real non-owner and a second ingest token come from a test-only `pg` connection to the local stack** (`tests/integration/support/privileged.ts`; never a service-role key, local hosts only). The non-owner is made by signing up and deleting that user's `app_owners` row, not by disabling the seed trigger, so no global state changes. The earlier plan note that Phase 2 would provide a non-owner session was wrong: it deliberately did not.
  - **The request guard is unit-tested in `npm test`** (`src/middleware.test.ts`) by resolving the `astro:` virtual modules with a Vite plugin and mocking their exports. It pins the Origin rule (missing, `"null"`, foreign, trailing slash, other port, other scheme all refused), the exact-path token exemption, and that `/api/ingest/` (trailing slash) is refused with 403, which fails closed. `src/lib/route-guards.test.ts` fails when a page or API route has no guard entry, because protection is a path prefix (`/dashboard`).
  - **Escaping is checked on the page by smoke** (markup in the recommendation text and in findings, visible and beyond the first five) and by a static guard that fails on `set:html`, `innerHTML` or `dangerouslySetInnerHTML` in `src` (`src/lib/render-safety.test.ts`). The surfaces that render lab or user text are listed in `context/archive/2026-10-02-testing-access-and-input-abuse/render-surfaces.md`.
  - **Known gaps, pinned:** (1) the database's `btrim` strips only spaces, so a tab-only or newline-only note passes the check while the server's `trim` refuses it (the server is the effective gate); (2) the server trims before it counts, so 500 characters plus surrounding spaces are saved, while the browser's `maxlength` counts the spaces; (3) owners can read `recommendations.push_id` because that grant is table-level, unlike the other tables.
  - **Not a gap:** emoji. The research assumed zod counted UTF-16 units like the browser; a run showed zod 4 and Postgres both count code points, so they agree and only the browser stops earlier (at 250 emoji).
  - **Owner writes to `day_notes` cannot ask for the row back** (`RETURNING` needs the unreadable `user_id` column), which is why `notes.ts` writes without `.select()`; the tests use the same call shape.
- **The app writes one JSON log line per failure with a request id, version and environment, and a sign-in provider outage is a 503 page, not a redirect (`context/changes/observability-capture-layer/`; owner's decisions from the 2026-10-03 observability audit).** _Why:_ before this, failed dashboard reads, a failed sign-in and an auth outage left nothing in the logs that said why, and an outage looked like a signed-out visitor.
  - **No tracker vendor yet.** The logger (`src/lib/logger.ts`) is tracker-agnostic: JSON to stderr with `ts`, `level`, `event`, `version` (`APP_VERSION`), `env` (`APP_ENV`) and the request fields. Errors keep name, message, `code`, `status`, `details`, `hint`, stack and up to three levels of `cause`.
  - **A request id on every request.** The middleware keeps an inbound `x-request-id` only if it is 8-64 characters of `A-Za-z0-9._-`, otherwise it makes one, and returns it as `X-Request-Id` and on the 503 page.
  - **Loader errors keep their cause.** Loaders throw `queryError(what, error)`, so the Postgres code (for example `42501`, a missing grant) reaches the log; each dashboard and history section logs `section_load_failed` with its label and still degrades on its own.
  - **An auth outage is a 503, not a redirect.** `getUser()` returns provider failures as `{ error }`; a network failure, a 5xx or a 429 on `/`, `/dashboard` or `POST /api/notes` answers 503 with `Retry-After: 30` and `Cache-Control: no-store`, and logs `auth_unavailable`. Sign-in routes keep working as anonymous. A missing session or an invalid token is still a silent redirect.
  - **No personal data in logs.** Emails appear only as `emailHash` (first 8 hex of SHA-256 of the trimmed, lowercase address); logged paths carry no query string, because `/auth/confirm` carries one-time tokens there.

## 2026-10-01

- **Three holes in the store's history rules are pinned by named known-gap tests and not fixed, and the push-to-page integration suite lives outside `src` with its own config (`context/changes/testing-push-to-page-integration/`; owner's decisions, test plan rollout Phase 2). No production code changed.** _Why:_ the store already guards replay, older pushes and narration in SQL, and a fix for each hole is a product decision, not a test fix.
  - **A newer capture replaces a stored total with a lower or empty one** (a daily total, a null daily total, an hourly row with fewer samples), pinned by three `KNOWN GAP` tests. Lab corrections downward can be legitimate, so a guard such as keeping the higher total would block a real correction; the app has so far avoided re-pricing or second-guessing the lab's numbers.
  - **A far-future `built_at` locks a summary row:** the contract accepts any ISO time and the row is replaced only by an entry whose `built_at` is the same or newer, so one such entry blocks every later current one. Pinned by one `KNOWN GAP` test; a fix is a contract bound or a comparison against now.
  - **A repeated `generated_at` silently keeps the first recommendation text** while the push answers 201. Pinned by one `KNOWN GAP` test; a fix is a 409 or an upsert, which changes what the lab sees.
  - **Five named tests in all** (`tests/integration/history-safety.test.ts`); each flips knowingly when a guard lands. The behaviour is stated in `docs/logic.md`.
  - **Non-owner and second-token tests are deferred to rollout Phase 3** (risks #6 and #7): both need postgres or service-role access that the anon-key suite deliberately does not have. Owner reads of the granted `ingest_pushes` columns are used where useful. _Done on 2026-10-05, see the entry above._
  - **Outside `src`, own config:** `tests/integration/` with `vitest.integration.config.ts` and `npm run test:integration`, so `npm test`, the `ci` job and Stryker stay stack-free and never need a database. In CI the suite runs after smoke in the `smoke` job and reuses its stack. It refuses non-local hosts and secret keys.
- **A future generation time is a problem on the recommendation and the today card, the bill forecast gets two more guards, and what stays unguarded is pinned by named known-gap tests (`context/changes/testing-time-and-number-guards/`; owner's decisions, test plan rollout Phase 1).** _Why:_ `ageStatus` called any negative age good, so a recommendation or narration time from a skewed lab clock read "aktualna" while the bill forecast already refused the same time; a test that pinned the old behaviour would have blessed the inconsistency. The tests-only alternative could not prove protection that did not exist.
  - **Future-time alignment:** more than 5 minutes ahead of the app's clock is a problem ("czas z przyszłości") on the recommendation and the today card, with the same 5-minute edge as the bill forecast (exactly 5 minutes ahead stays current). The recommendation card says the clock is wrong instead of "Laboratorium mogło przestać przesyłać dane.", because a future time is not an outage, and its forecast days use date-only labels. The live state is left alone: its `captured_at` is already checked at receipt.
  - **Two bill-forecast guards:** the 7,000 PLN ceiling now also covers the closed-month check's computed and invoice amounts (the contract has no ceiling, so this was a reachable hole), and a negative central, low, high or closed-month amount is refused. The sign guard is defence in depth only, since the contract already rejects negatives with a 422. The ceiling sits before the day count, so a body with fewer than 7 days and an absurd closed-month amount now shows "nierealna kwota" instead of "Za mało dni".
  - **Two gaps pinned, not fixed:** no lower plausibility bound (a central below the 44.62 PLN fixed fee still shows) and no consistency check between the central and its own billable kWh × rate + fee. Both would need a view-model rule the app has avoided so far (it does not re-price); the named `KNOWN GAP` tests flip when one is added.
  - **Low-sun rounding left unfixed and pinned:** PV 13,96 against a norm of 20 is flagged low while the text prints "14,0 … 20,0". A fix needs edge labels as the usage insight has them; it is a separate change, and the test flips when it lands.
  - **App-side oracle only:** the tests derive expected values from `docs/logic.md` and hand arithmetic written in comments (verdict bands, delta, ceiling, 7-day rule, display rounding), not from the lab's projection formulas, which the app never runs.
  - **Follow-up:** `docs/ingest/example-v1.json` is treated as real household data (a test comment calls it "the real September body"), so the new fixture (`closed-month-amount-above-ceiling.json`) and the figures in the new tests are invented. The shared `okRow` base in `bill-forecast.test.ts` and the older tests that build on it still carry the example's values. Scrubbing the example, and the tests that read it, is a separate change.
- **The period texts (S-18) are shown as narrated, on a dashboard card under the recommendation and in the calendar's completed day and month views, with no figures from `facts` (`context/changes/period-summaries/`; owner's decisions).** _Why:_ the grid and house-use figures in `facts` are unreliable for the whole history ([Grid sensor caveat](logic.md#grid-sensor-caveat)), so showing facts would show numbers nobody can trust; the lab's text already says what its facts mean without quoting them.
  - **One neutral sentence for a missing narration:** a row with facts but no text shows "opis jeszcze się nie pojawił" and the covered period, no figures; a period with no row shows no calendar panel at all, and the dashboard says the lab has sent nothing.
  - **Today's staleness is the recommendation's rule:** older than 2 hours by the time the card shows as "Wygenerowano" (the text's generation time, falling back to `built_at`), or from an earlier Warsaw day, with the same three badge wordings (one shared helper in `recommendation.ts`) ("aktualna", "sprzed …", "z <data> — dotyczy innego dnia"), so two cards side by side age in the same way. _Extended 2026-10-01:_ a time more than 5 minutes ahead of the clock is a problem ("czas z przyszłości") on both cards, see the entry above.
  - **Placement:** the card sits under the recommendation in the wide column, because it explains the same day's figures; the calendar panel sits directly under the rating.
  - **No quarter summary and no today-in-calendar summary:** the lab writes no quarter texts, and today's text lives on the dashboard.
  - **A failed calendar load shows nothing,** while the dashboard shows a load-failed card: the panel is decorative on the calendar, and a month summary cannot render when the month view itself failed.
  - **No model label:** the roadmap asks only for the generation time and the covered period.
- **Day notes (S-19) are one note per day, on days from 2026-07-16 through today, in an author-and-owner table that is the app's first client write, edited with plain forms and no client JavaScript (`context/changes/day-notes/`).** _Why:_ the PRD's wording is singular ("a note to a calendar day") and one note per day keeps the month marker a simple yes/no; history plus today covers the use the owner wants ("urlop", "pompa ciepła od dziś") without opening future days, which the calendar can't show anyway (owner's decisions).
  - **Author and owner:** every policy on `public.day_notes` requires both `user_id = auth.uid()` and the `app_owners` check, as the dropped S-05 feedback design did: the PRD scopes notes to the signed-in user, and the codebase scopes every client read to owners. `user_id` is defaulted by the database and never granted, so a client cannot write someone else's note even if a policy were wrong.
  - **No client JavaScript:** the history page has none by design, so the forms post natively to `/api/notes` and native `<details>` open the form and the delete step. Deleting asks for confirmation ("Usuń", then "Na pewno usuń"), because there is no undo. A second submit of the same form is harmless, so no double-submit guard is needed.
  - **Update, then insert, instead of an upsert:** an upsert needs `on conflict (user_id, day)`, and the client may neither read nor write `user_id`, so PostgREST can't target that conflict. The route updates the day's note, inserts one when no row changed, and retries once as an update if a concurrent insert loses on the unique constraint (SQLSTATE `23505`). Granting `user_id` to make the upsert work would have weakened the security model.
  - **Writes go through `/api/notes` only,** so the middleware's `Origin` check covers them; the route checks the session itself.
  - **Notes stay in the app:** they never reach the lab or an LLM and never change ratings, summaries or recommendations.
- **Period summaries (F-04) are written in the lab by the cloud model alone, from facts that travel with them, and stored in the app one row per period with the latest `built_at` winning (`context/changes/lab-period-summaries/`; owner's decisions on the research questions).** _Why:_ the texts must describe without advising and introduce no numbers of their own, and a failed LLM call must not cost the facts (owner's decision 2026-09-30). Display is S-18, not this change.
  - **Facts:** PV against the forecast, battery cycling and the season from the date. Grid import, export and house use stay in the facts flagged unreliable and are never quoted in a text, because the grid sensor is wrong for the whole history. The local model's observations are left out for now: 97% of them are fixed rules on those faulty counters.
  - **Cloud only, facts kept:** when OpenRouter fails, the entry goes with `narration: null` instead of a text from Ollama, and a later run fills it in. The lab re-sends each period's last accepted text, so a push never downgrades a narrated period.
  - **Today is its own hourly call,** with facts and text built together so they always match (about 4 USD a month more), rather than riding the advisory call, whose prompt is shaped for advice.
  - **Latest wins, not first wins:** a backfill or a fix can replace a stored text; `built_at` decides, so a late retry of an older push cannot.
  - **Only complete periods:** no text for an incomplete day or for a month with fewer than 7 complete days; the month text runs from the 1st.
  - **A lab numbers check** drops a text that quotes a number missing from its facts; the app shows the text as narrated.
  - **Backfill** of 2026-07-16 to 2026-09-30 (days, July, August and September) once, in batches of at most 14 days, and the advisory's SSL crash (`request_json`) is fixed in the same change, since the summary job reuses that client.

## 2026-09-30

- **Grid import and house use carry one caveat for the whole history, and the afternoon of 3 August 2026 is named only as the moment the inverter's grid sensor changed direction (4 August is the first whole day after it); nothing is corrected numerically (option A, owner's decision 2026-09-30, `context/changes/inverter-grid-correction/`).** _Why:_ an hourly comparison of PGE's meter data with the inverter (16 July – 31 August 2026, aggregates only) showed the grid sensor wrong from the first day, not only from August. Before the change the inverter's hourly net fits about −0.53 × PGE's net − 0.70 kWh, after it about +0.53 × PGE's net + 0.70 kWh, so July's import read 151 kWh against PGE's hourly-balanced ~350 and August's export 95 against 342. House use is derived from the same sensor, so it carries the same caveat. The app's earlier note blamed only the days from 4 August, which was wrong on both sides of that date. The caveat comes from one module (`src/lib/services/grid-sensor.ts`) and shows on the live, usage, hourly and bill forecast cards and in the history page's captions and "Co to znaczy?" (`docs/logic.md`, Grid sensor caveat).
  - **Ratings:** across the change the import error flips sign, so a 14-day norm reaching across it compares days that are not comparable. The mixed day 2026-08-03 and the days to 2026-08-17 read "Poza oceną" with a neutral basis naming the sensor change, and no norm mixes days from both sides; August is rated from its post-change days only (18 August on), even where 1–2 August are rated as days (owner's choice at the production check). The usage card adds a note when its baseline spans the change.
  - **Option B, a fitted correction, rejected:** the hourly formula is unverified (R² 0.90 after the change, fitted on import-only hours over 6.5 weeks), it would need a lab re-push because the app keeps hourly nets for 35 days only, and it would show numbers no meter measured.
  - **Option C, PGE figures for closed days, is a separate later change:** a lab aggregation and push, a contract section and a migration, and first the parked privacy decision (roadmap, Parked). Until then the history before the physical fix stays as it is, with this caveat.
  - **Option D, the installer's on-site check** of the sensor's placement and phase mapping, runs in parallel outside the app. The app does not depend on it, so it is tracked in roadmap question 5, not in `docs/prerequisites.md`.

- **Completed days and months are rated good / neutral / bad by self-sufficiency against a recent 14-day norm, with a ±10 percentage-point band (S-17, `context/changes/period-ratings/`).** _Why:_ self-sufficiency (`1 − import ÷ use`) is bounded to 0–100% and higher is better, so a relative ±% band like the usage card's would mean different things at 30% and at 70%; absolute points read plainly ("25,0 punktu poniżej normy"), and exactly ±10 stays neutral by the same edge rule as the other verdicts.
  - **14 days, not 30:** the norm is the median of the qualifying days in the 14 days before the rated day, needing at least 7. It follows the autumn slide twice as fast as a 30-day window, which answers roadmap question 8 for the ratings; the usage card keeps its 30 days.
  - **The month is rated by the median of its rated days' gaps** from their own norms, with the same ±10 rule and at least 7 rated days, so it is immune to the seasonal slide that comparing one month with the previous one would suffer. The current month, today, future days and the quarter are not rated.
  - **Green / grey / red:** neutral uses the grey tone with its own word ("Przeciętny dzień"), because amber already means "warto sprawdzić"; "Za mało danych" and "Poza oceną" are grey with their own words.
  - **Days with import above use are skipped:** a day whose import exceeds its use (the early rows of roadmap question 7) reads "Poza oceną" and never enters a norm. The wording is neutral ("np. ładowanie baterii z sieci albo błąd licznika") because charging the battery from the grid would be a real day, not an error (implementation review F2). Cloudy days are still rated, with a "Mało słońca" note when PV is under 70% of the norm days' PV, because self-sufficiency mostly follows the sun and the note gives the cause. The grid sensor's error flips sign at its direction change on 3/4 August 2026, so a 14-day norm reaching across the change does not cancel it: the days 2026-08-03 to 2026-08-17 read "Poza oceną" with a basis naming the sensor change, and no norm mixes days from both sides (`inverter-grid-correction`, entry above; this replaces the earlier reasoning that the error was the same on every day).
  - **Placement:** the day view (under "Dzień w liczbach") and the month totals only, as the owner chose; not in the month grid, the quarter or the dashboard. The month's panel sits beside `TotalsPanel`, which the quarter also uses and which stays unrated.
  - **No seasonal norm yet:** same-season history won't exist before about July 2027, so every rating uses the recent norm and says so in its basis.

- **The history calendar (S-15) is day, month and quarter at `/dashboard/history`, with the period in the URL (`?day=`, `?month=`, `?quarter=`) and "Pulpit / Historia" links in the header; the year view stays in S-16.** _Why:_ history reaches back only to 16 July 2026 and the roadmap already splits the partial-year view out as S-16. A path under `/dashboard` is covered by the existing protected prefix, needs no middleware change, works with no JavaScript and can be bookmarked; an invalid or out-of-range period redirects to the default month. With no period the page opens on the current month from its 7th complete day and on the previous month before that, so it never opens on an almost empty "za mało danych" page early in a month. Totals are sums over complete days with their day count, reusing the 7-day minimum, and are never extrapolated (`context/changes/history-calendar/`).
  - **Left out:** the inverter's grid export (it under-reads and shows 0 from about mid-August while PGE recorded real export) and PGE figures (showing them needs an owner decision on privacy first; parked in the roadmap); both are explained in "Co to znaczy?". No hourly chart in the day view, because the app keeps hours for 35 days only, so days would behave differently. The ten missing and five empty days are not filled here: they stay gaps, and a separate lab change can re-send them from Home Assistant's hourly statistics with the `--from/--to` push (a roadmap follow-up).
  - **Shared page shell:** `AppShell.astro` (aurora background, header with the brand `h1` and the navigation, one `<main>`, an optional legend footer) is extracted from the dashboard's body so both pages share landmarks and layout; the dashboard's markup is otherwise unchanged and its 5-minute reload stays on the dashboard only, since past periods don't change.
  - **Historical recommendation view:** `toRecommendationView(row, now, { historical: true })` gives a past day's advice a neutral badge with its generation time, no stale flag and the findings' real colours, and the day view has its own "Rekomendacja z tego dnia" section instead of the dashboard card, which would call every past day's advice "dotyczy innego dnia" in red. The day shows its first recommendation from 06:00 (the one that set the battery plan) and folds the rest.
  - _Superseded 2026-09-30 (`inverter-grid-correction`, entry above):_ the calendar no longer notes grid import as over-reported from 4 August only; grid import and house use carry the whole-history sensor caveat, and 4 August is named only as the day the sensor's direction changed.
  - The invalid-period redirect is set on `Astro.response` rather than returned from the frontmatter, because a top-level `return` there crashes typescript-eslint's `no-misused-promises` rule.

- **The ten backfilled days (2026-07-16 to 2026-07-25) are kept as the lab sent them, including the four that don't balance (07-18, 07-21, 07-23, 07-24: PV + import and house use + export differ by 8–32 kWh).** _Why:_ the early PV and export counters are off, and the days already stored from the same period (such as 07-26 and 07-27) have the same gap under the same day rules; holding them back would take a new plausibility rule, which applies to every day and belongs in its own change (`history-backfill`, owner's decision after the dry run).

- **Hourly totals per clock hour may now leave the lab (`hourly_history`), for a "Godziny zużycia" card; this reverses S-10's "only hour-of-day aggregates may leave, never single readings or timestamps" for the inverter's own figures.** Still no sub-hour readings and no raw PGE rows leave the lab. _Why:_ the owner's real concern is how much the house draws from the grid at night, and which hours and days use the most and the least, and that needs one row per clock hour with its time. The card rates nothing, so its badge is neutral and names the complete days its figures rest on (`context/changes/grid-export-mismatch/frame.md`).
  - _Correction (2026-09-30, after the production backfill):_ "agrees with PGE at night" overstated it. Over 26–31 August (22:00–06:00) the inverter read 11.8% above PGE's hourly-balanced import, single nights +5% to +21% (`docs/logic.md`, Godziny zużycia).
  - _Superseded 2026-09-30 (`inverter-grid-correction`, entry above):_ the sensor is wrong for the whole history, not only since 4 August, and at low load its fixed offset dominates, so the card no longer gives a night percentage or says the reading is over-reported from 4 August; it shows the shared sensor caveat.
